# 非预留服务器集中暖服设计

## 目标

空闲 Warm-up Agent 应优先填充已经存在暖服的非预留 Target Server，避免同一批
Agent 因同优先级轮询被拆到多个普通服务器。目标达到本轮可用容量或无法通过实时
准入检查时，调度器应继续尝试下一个已有暖服目标；所有已有目标都无法接收时，才
回到新目标的 priority 与轮询规则。

## 根因

`WarmupSchedulerService` 在没有可续暖目标时逐个规划 Agent。每次规划都会更新
`plannedCursorTargets`，而 `WarmupDecisionEngine.SelectNextTarget` 对同优先级目标
从游标之后开始轮询。因此 A、B 同优先级且 A 仍有容量时，首个 Agent 选 A，后续
Agent 会轮到 B。当前续暖路径只覆盖仍在共享 `AttemptWindow` 内的普通目标，不能
覆盖首批启动或无法续暖的情况。

## 调度顺序

每个空闲 Agent 依次使用以下顺序：

1. 已触发的同目标重建请求。
2. 有活动 `active`/`uncertain` 暖服且仍有容量的非预留目标，按当前暖服数降序，
   并列时按 `priority` 降序和稳定 ID 排序。目标仍受共享尝试窗口约束。
3. 如果第 2 层的目标已满、A2S 人数达到 `PlayerTarget`、DNS/A2S 不可用或计划
   失败，则继续检查下一个已有暖服目标。
4. 没有任何已有普通目标可接收时，执行现有新目标选择：`priority` 降序，同优先级
   使用持久化 round-robin；普通目标和预留目标仍按各自并发/租约规则过滤。

规划状态在同一 tick 内即时增加目标计数，所以一个目标能接收几个 Agent 就先接收
几个，剩余 Agent 再按上述顺序回退。Agent 启动请求失败继续沿用当前不确定状态和
隔离语义，不在同一 tick 复用该账号。

## 兼容边界

- 预留目标不参与集中普通暖服偏好，仍固定有效并发为 1，并保留 reservation lease
  与空服准入检查。
- 不改变 `MaxConcurrentWarmups`、`PlayerTarget`、A2S/DNS 检查、共享尝试窗口、
  同目标重建或批次启动上限。
- 不增加数据库实体或迁移；集中排序只使用现有活动 attempt 计数和目标配置。
- 只有第 2 层没有可接收目标时才使用新目标轮询；因此现有 priority 轮询在新一轮
  暖服和普通目标均不可续暖时保持兼容。

## 验收与测试

- 同优先级、均有容量的两个普通目标，在一个 tick 的多个 Agent 中只填充首个目标。
- 已有普通暖服目标的当前计数高于另一个已有目标时，后续 Agent 继续选择计数更高者。
- 首个已有目标只能接收部分 Agent 时，剩余 Agent 回退到下一个已有目标，若无则
  回退到新目标 priority/轮询。
- 目标满容量、A2S 达到人数目标或 A2S 失败时，会跳过该目标并继续回退。
- 预留目标不获得集中普通暖服偏好；既有重建、共享时间窗、租约和启动失败测试继续通过。
